### 问题一：剪映 11.2+ 草稿被设备级 AES 强加密，如何直接二次读取修改

- **现象**：
  打开已有草稿目录，发现 `draft_content.json` 开头为 `H453QXuFDa` / `I5Bi` 等 Base64 加密乱码。
- **根本原因**：
  剪映从 11.2 开始推行设备级 AES 加密机制，将 JSON 序列化后通过本地 `videoeditor.dll` 加密为 Base64 落地磁盘。
- **终极破解解决方案（⭐⭐⭐ 2026重大突破）**：
  采用集成自 `aoguai/pyJianYingDraft` (commit `80d521b`) 的 `JianyingDraftCryptoCodec`，直接挂接剪映本地的 `videoeditor.dll`，实现双向无损加解密：
  ```python
  from pyJianYingDraft import JianyingDraftCryptoCodec, DraftCryptoConfig
  from pyJianYingDraft.draft_codec import write_json_object_with_codec

  codec = JianyingDraftCryptoCodec(DraftCryptoConfig(
      jy_install_dir=r"C:\Users\trees\AppData\Local\JianyingPro\Apps\11.4.1.14443",
      isolated=True, validate_roundtrip=False, backup=False
  ))

  # 1. 内存直接解密已有加密草稿
  raw_bytes = open("draft_content.json", "rb").read()
  draft_dict = codec.decode(raw_bytes)

  # 2. 修改业务逻辑（增删片段/注入关键帧/调色等）...

  # 3. 原地重新加密写回
  write_json_object_with_codec("draft_content.json", draft_dict, content_codec=codec, indent=None)
  ```
  **彻底告别只能新建空白工程的妥协方案，直接原地修改剪映现有工程！**

### 问题二：多切片视频中「仅首片段关键帧生效，后续片段全部静止死值」

- **现象**：
  长视频切片为几十个小片段后，只有第 1 个片段有呼吸缩放动画，从第 2 个片段开始缩放完全静止（固定在某个数值）。
- **根本原因（⭐⭐⭐ 核心避坑）**：
  剪映底层引擎对多切片视频关键帧的 `time_offset`（时间偏移量）定义是**「相对于源素材物理起点（Source Media Time）」**，而不是片段内的相对时间（0 ~ Duration）。
  - **首片段**：`source_start = 0`，关键帧打在 `0s ~ 1.2s`，落在播放区间内 ➡️ **生效**。
  - **后续片段**：例如第 2 片段物理起点是 `1.2s`，如果关键帧依然打在 `0s ~ 1.2s`，剪映会认为关键帧在过去早已播放完毕，导致整个切片只显示最后一帧的固定值 ➡️ **失效**。
- **代码解决方案**：
  ```python
  # 必须对齐物理源起始时间轴：
  source_start_us = int(start_sec * 1_000_000)
  
  # 循环每个切片内部的关键帧：
  local_t_us = 0
  while local_t_us <= seg_dur_us:
      exact_source_time = source_start_us + local_t_us  # 核心对齐！
      seg.add_keyframe(KP.scale_x, exact_source_time, scale_val)
      seg.add_keyframe(KP.scale_y, exact_source_time, scale_val)
      local_t_us += step_us
  ```

### 问题三：切片中打入过多关键帧导致密集如刺猬，画面眩晕且无缩放效果

- **现象**：
  时间线上片段内密密麻麻全是关键帧菱形，画面震颤或者缩放完全不生效。
- **根本原因**：
  1. 使用了高频正弦/余弦采样点（每 0.3s~0.4s 打一个点），导致一个切片生成了几十个点。
  2. 误往全局 `keyframes.videos` 和 `keyframe_refs` 注册了多余的无用引用，与片段内部原生解析发生冲突；
  3. `uniform_scale` 被篡改成 `{"on": True}` 导致面板强制过滤独立轴。
- **标准解决方案（植人大树 极简柔和呼吸运镜体系）**：
  1. **极简双点 / 三点律（拒绝高频密帧）**：
     - 单个镜头只需设定 **2 ~ 3 个关键帧点**，完全交给剪映底层进行贝塞尔/线性平滑过渡。
     - **短片段（< 1.5s）**：首尾两点线性缓动（`1.000 ➔ 1.055` 或 `1.055 ➔ 1.000`）。
     - **长片段（> 2.0s）**：三点柔和呼吸：
       - 起点：`1.000`
       - 中点：`1.035`（微呼吸）
       - 终点：`1.055`（平滑收止）
  2. **完美支持等比缩放**：
     - 在 `seg["common_keyframes"]` 中同时注入 `KFTypeScaleX` 和 `KFTypeScaleY`，两者的关键帧时间偏移与数值完全保持一致；
     - `seg["uniform_scale"] = {}`（保持原生空字典），在剪映前台既支持等比缩放滑块，又不会发生冲突。
  3. **数据层级极简**：
     - `seg["keyframe_refs"] = None`；
     - 全局 `draft["keyframes"]["videos"]` 保持清空；
     - 直接挂载在 `common_keyframes`，剪映原生渲染器秒级识别。

### 问题四：剪映提示「无法打开草稿，草稿内容已损坏」

- **现象**：
  生成的草稿在剪映列表中点击时弹出弹窗：「无法打开草稿，草稿内容已损坏，请联系客服获取修复帮助」。
- **根本原因**：
  1. **属性冲突**：`UNIFORM_SCALE`（等比缩放）与 `KFTypeScaleX` / `KFTypeScaleY`（独立轴缩放）在剪映底层是**严格互斥**的，同时写入同一个片段会导致 JSON schema 校验直接崩溃。
  2. **虚构时间线目录**：手动伪造 `Timelines/<Random_UUID>/` 目录但未在 `draft_meta_info.json` 中建立正确索引链。
- **代码解决方案**：
  1. 缩放属性使用 `KP.scale_x` 和 `KP.scale_y` 组合，严禁与 `uniform_scale` 混写。
  2. 统一通过官方封装的 `pyJianYingDraft.ScriptFile` 或 `JyProject` 进行 `save()` / `dump()` 导出，避免直接手写篡改底层元数据结构。

### 问题五：面板滑块未点亮关键帧菱形图标 `< ◆ >`

- **现象**：
  视频播放时画面确实在放大缩小，但在右侧属性面板中，「缩放」旁边的菱形图标依然是空心 `< ◇ >`。
- **根本原因**：
  剪映右侧属性面板只在**时间线指针（Playhead）精确停留在关键帧所在的微秒刻度上**时，才会将菱形点亮为实心 `< ◆ >`；如果在两帧之间，图标默认保持 `< ◇ >` 并显示实时插值计算出的数值。此现象属于剪映正常交互设计，只要画面在动态缩放即代表关键帧生效。

## 📋 快速排查速查表 (Quick Cheat Sheet)

| 检查项 | 验证标准 | 错误后果 |
|:---|:---|:---|
| **加密草稿修改** | `JianyingDraftCryptoCodec` 内存加解密 | 外部直接修改报错乱码或草稿已损坏 |
| **关键帧密度** | 单片段仅 2~3 个柔和缓动点（首尾/中） | 高频正弦密帧导致刺猬密集与严重眩晕 |
| **等比缩放支持** | `common_keyframes` 内 X/Y 数值完全同步，`uniform_scale: {}` | 缩放失效或互斥被屏蔽 |
| **关键帧时间戳** | `offset = source_start_us + local_offset` | 仅第 1 个片段有效，后续切片全部死值 |
| **数据层级清洁** | 挂载于 `common_keyframes`，`refs` 置 None | 冗余引用导致面板属性打架不生效 |
| **混合模式** | FX Overlay 必须 `blend_mode = "screen"` | 遮挡主画面黑屏 |
